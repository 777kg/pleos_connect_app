# 기획 화면 산출물 (와이어프레임 → UI 설계서 → 지속 갱신)

기획서(`docs/plan/PLAN.md`)를 화면으로 옮기는 규칙입니다. 산출물은 모두 `docs/plan/ui/` 아래에 둡니다.
차량 앱 규칙은 `pleos-connect-dev` 스킬(SKILL.md Core Rules, cheatsheet)을 그대로 따릅니다.

## 1. 단계 판단

`PLAN.md` 맨 위 상태 줄의 **`UI 단계`** 값으로 정합니다. 값이 없으면 아래 기준으로 판단해 상태 줄에 적습니다.

| UI 단계 | 언제 | 만드는 것 |
|---|---|---|
| `wireframe` | 주제·핵심 기능은 있지만 문구·상태·수치가 덜 정해짐 | 화면별 저충실도 HTML 와이어프레임 + `SCREENS.md` |
| `spec` | 기능·상태·문구가 정해지고 구현을 앞둠 (사용자가 요청하거나 PLAN.md 미결 질문이 대부분 풀림) | `UI_SPEC.md` + 와이어프레임을 설계서와 맞게 갱신 |
| `update` | `spec` 이후 기획이 바뀔 때마다 | 바뀐 화면·설계서만 고치고 `CHANGELOG.md`에 기록 |

- 단계는 앞으로만 갑니다. 되돌릴 때는 사용자의 결정이 있어야 하고 `DECISIONS.md`에 남깁니다.
- 어느 단계든 **PLAN.md와 화면이 어긋나면 화면을 PLAN.md에 맞춥니다.** PLAN.md에 없는 기능을 화면에서 먼저 만들지 않습니다. 필요하면 PLAN.md 미결 질문으로 올립니다.

## 2. 파일 구조

```
docs/plan/ui/
  SCREENS.md            화면 목록(ID, 이름, 목적, 상태 목록, 파일, 버전)
  wireframes/
    S01-<이름>.html      화면 하나 = 파일 하나. 템플릿: templates/wireframe.html
  UI_SPEC.md            spec 단계부터. 템플릿: templates/UI_SPEC.md
  CHANGELOG.md          update 단계부터(또는 첫 갱신부터). 템플릿: templates/CHANGELOG.md
```

- 화면 ID는 `S01`, `S02`…로 붙이고 바꾸지 않습니다. 화면을 없애면 `SCREENS.md`에 "삭제(날짜·이유)"로 남깁니다.
- 각 와이어프레임 파일 머리에 `버전 vN · 날짜 · 근거(PLAN.md 절)`을 적고, 고칠 때마다 N을 올립니다.

## 3. 와이어프레임 규칙 (wireframe 단계)

- `templates/wireframe.html`을 복사해 씁니다. **HTML 한 파일, 외부 리소스(폰트·CDN·이미지) 없이** 브라우저로 바로 열리게 합니다.
- 회색조 저충실도: 상자·텍스트·번호 주석만. 색은 상태 구분이 꼭 필요할 때만 쓰고 범례를 붙입니다.
- **한 파일에 프레임 여러 개**를 나란히 둡니다.
  1. portrait 1칸 (기본 상태)
  2. landscape 2칸 (같은 기능, 다른 배치)
  3. 상태별 프레임: 로딩 / 값 수신 / 미지원(capability 없음) / 권한 없음 / 값 미수신(오류) / **주행 규제** — 화면에 해당하는 것만
- 프레임 크기는 실제 해상도가 문서에 없으므로 **비율만 가정**합니다(템플릿 기본: 1칸 360×640, 2칸 720×640). 프레임 아래에 "크기는 가정, 실제 해상도·dp 확인 필요"를 남깁니다.
- 요소마다 번호 주석(①②…)을 달고, 프레임 옆 주석 목록에 "무엇·왜·데이터 출처(API)·규칙"을 적습니다.
- 차량 앱 제약을 화면에 드러냅니다.
  - 큰 터치 영역, 적은 텍스트, 단순한 메뉴. 텍스트 입력 대신 프리셋·최근 항목·음성.
  - 두 방향 모두 **같은 기능**(기능 패리티), 레터박스 없음.
  - 정차 중 전용 앱은 주행 규제 프레임에 값·조작이 보이지 않아야 합니다.
  - Back은 화면을 닫지 않고 앱을 숨깁니다(최상위). 다른 화면으로 가는 흐름이 있으면 화살표로 표시합니다.
- `SCREENS.md`에 화면 흐름(어디서 어디로, 무엇을 누르면)을 목록이나 mermaid로 적습니다.

## 4. UI 설계서 규칙 (spec 단계)

`templates/UI_SPEC.md` 구조를 따릅니다. 화면마다 다음을 채웁니다.

- **레이아웃**: portrait/landscape 영역 배치, 스크롤 영역, 리사이즈 시 보존할 상태
- **컴포넌트 표**: ID · 종류(텍스트/카드/버튼…) · 내용·문구 · 데이터 출처(API·퍼미션) · 상태별 표시 · 동작
- **상태 표**: 로딩 / 정상 / 미지원 / 권한 없음 / 오류 / 주행 규제 / 숨김→복귀 — 각 상태에서 보이는 것과 숨기는 것
- **문구 목록**: 화면에 나오는 모든 한국어 문구(키 이름 제안 포함, 예 `check_title`). 진단·보증처럼 보이지 않게
- **동작·이벤트**: 버튼, 규제 변경, 리스너 갱신, 생명주기(onStart/onStop)
- **접근성·운전 중 배려**: 터치 영역, 대비, 글자 크기 — 수치는 UI Design Guide에 없으면 "확인 필요"로 남기고 임시값을 적습니다
- **구현 메모**: 기존 코드 구조(README의 클래스)와 연결되는 지점. 코드는 쓰지 않습니다
- 설계서와 와이어프레임은 같은 화면 ID·컴포넌트 ID를 씁니다. 설계서를 고치면 와이어프레임도 같은 실행에서 맞춥니다.

## 5. 지속 갱신 규칙 (update 단계, 그리고 모든 갱신)

1. 이번 요청과 `DECISIONS.md`의 새 결정을 읽고 **영향받는 화면 ID**를 먼저 적습니다.
2. 그 화면만 고칩니다. 관련 없는 화면·문구는 건드리지 않습니다.
3. 와이어프레임 버전·날짜를 올리고, `UI_SPEC.md`(있으면)와 `SCREENS.md`를 같이 맞춥니다.
4. `CHANGELOG.md`에 한 줄 추가: `날짜 · 화면 ID · 무엇이 바뀜 · 근거(결정/PLAN 절)`. 지우거나 고쳐 쓰지 않습니다.
5. 최종 보고에 "바뀐 화면: S01 v2 → v3" 형식으로 적습니다.

## 6. 하지 않는 것

- 실제 앱 코드·레이아웃 XML·리소스 작성(구현은 메인 담당). 이미지 생성 대신 HTML·텍스트로 그립니다.
- 공식 수치(해상도, dp, 버튼 크기, 글자 크기)를 지어내기. 모르면 "가정"·"확인 필요"로 표시합니다.
- PLAN.md에 없는 기능을 화면에 추가하기, 주행 중에 금지된 요소(동영상, 차량 설정, 긴 텍스트, 키보드 입력)를 주행 상태 프레임에 넣기.
